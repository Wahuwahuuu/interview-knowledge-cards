# 主问题与追问的组织规范

题库按语义组织。判断主问题时，先找到它依赖的基础概念或完整流程，不以原材料的段落、第一句话、问号顺序或关键词相似度决定父子关系。

## 什么可以成为主问题

- 能独立解释一个知识点，例如联合索引、MVCC、分布式锁。
- 能独立讲清一个完整流程，例如 SQL 执行、Agent Loop、RAG 检索生成。
- 完整的系统设计或算法任务，例如短链系统设计、链表反转。不能为了减少入口，把所有系统设计题塞进一个空泛的“系统设计”主问题。

主问题应有自己的口述答案与详细讲解。缺少基础题时，可以补一张有实际内容的概念卡，不能只新增一个没有答案的分类标题。

## 哪些内容适合作为追问

实现机制、方案对比、边界条件、异常处理和具体例子，放在理解它所必需的主问题下面。追问也必须独立可读，并保留自己的答案。

例如：

- 什么是联合索引？
  - 什么是最左前缀原则？
    - 范围条件如何影响后续索引列？
      - 给定索引 `(a,b)` 与一条具体范围查询，如何分析索引利用？
  - 联合索引的列顺序如何设计？

索引下推、覆盖索引等独立知识点可以通过 `related` 关联；不能仅因某条 SQL 同时涉及这些知识点，就复制卡片或让它在多个主问题下重复出现。

## 关系与顺序

- 一个在用追问只保留一个直接父问题；跨知识点、跨项目使用 `related`。
- 追问按“基础解释 → 原理 → 取舍或边界 → 具体场景”排列，填写 `order`。
- 通常控制在三层追问以内。更深时检查是否可以提升为独立知识点。
- 不同题目仅共享关键词，不代表存在追问关系。例如消息可靠性和消息顺序可以是两个独立知识点。
- 检查整个组的语义与顺序，不能只逐条判断每条连线是否有共同词语。

## 重复题与资料保护

普通导入不能擅自语义合并。用户明确要求全库整理或去重时，才判断两题是否具有相同主体、前提、任务和答案范围；改变前提的场景题与比较题通常应保留。

确认同义后选择一张可维护的卡片作为入口，整理其答案，将有效追问转接到合适位置。重复原卡采用“归档保留”，保留原问题、原答案、掌握状态和来源；需要时为保留卡片新增来源关联，不覆盖旧出现记录。跨项目重复题统一入口后，使用相关问题保持发现路径。

整理前保存当前题库快照，整理后检查：每张在用卡片均能从一个主问题到达、无环、无多父问题、没有丢失原卡片与原始来源。修改前重新读取最新记录；并发变更时停止覆盖，按最新内容重新核对。

真实题库、整理映射、快照和逐题报告保存在被忽略的私人目录，不提交到公共仓库。
